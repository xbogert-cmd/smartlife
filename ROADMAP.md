# SmartLife Roadmap

SmartLife is a local-first macOS desktop app (Electron) unifying school (Canvas),
Google Calendar, an embedded browser, tasks/notes/goals, and a multi-provider AI
assistant with tool-calling and explicit permission tiers.

This roadmap supersedes the original master-build-prompt's phase list: same
destination, but resequenced where a real dependency was missed, and with
external-setup/cost gates called out per phase so nothing gets built on top of
an assumption that turns out to be wrong. Each phase gets its own
brainstorm → spec → plan → subagent-driven-implementation cycle when we reach
it — this file just tracks order and dependencies, not per-phase detail.

## Corrections to the original prompt

The pasted prompt was a strong starting brief, but seven things in it don't
survive contact with reality. Fixing them now avoids building on a false
assumption later:

1. **"Detect an existing Claude API credential"** — there isn't one to detect.
   A Claude Code / claude.ai subscription doesn't expose a reusable API key to
   other apps. SmartLife needs its own key from console.anthropic.com, billed
   separately (pay-as-you-go) from the Claude subscription. Already resolved —
   user has a key ready for Phase 2.
2. **Canvas OAuth** — the prompt assumes an OAuth flow, but registering an
   OAuth developer key on a university Canvas instance typically requires
   institutional admin approval, which a student account won't have. Canvas's
   **personal access token** (self-service, generated by the user in Canvas
   Settings → Approved Integrations, no admin involved) is the realistic path
   for Phase 3 and is what we'll build against.
3. **Submission workspace sequencing** — the prompt puts the full submission
   workspace (including "fall back to the embedded browser when the API can't
   handle a submission type") inside Phase 3, but the embedded browser doesn't
   exist until Phase 5. Split into **Phase 3 (read-only Canvas: courses,
   assignments, grades, sync)** and **Phase 3b (submission workspace + actual
   submission)**, with 3b resequenced after Phase 5 so the fallback path has
   something to fall back to.
4. **`keytar` / generic "secure OS credential storage"** — `keytar` (the
   library most guides suggest) is deprecated and unmaintained. Electron ships
   a built-in `safeStorage` module (OS Keychain-backed on macOS) that does the
   same job with no extra native dependency — use that instead.
5. **External cron/polling service** — the dashboard project (a serverless
   Next.js app) needed an external scheduler (cron-job.org) to poll for
   calendar sync because nothing runs when no one is browsing it. SmartLife is
   a persistent local desktop app — it can just run an in-process interval
   timer while open, plus sync on launch/focus/manual refresh. No external
   scheduler needed; genuinely simpler than the web app's approach.

6. **Google OAuth client reuse** — an earlier version of this file said Phase 4
   could reuse the dashboard project's OAuth client by adding a redirect URI. It
   can't. The loopback redirect (`http://127.0.0.1:PORT`) that installed apps must
   use requires an OAuth client of type **Desktop app**; the dashboard is a web app
   and its client is type **Web application**, which is fixed at creation and will
   not accept a loopback URI. The real shortcut is one level up: reuse the same
   Google Cloud *project* and consent screen, adding a second Desktop app client.
   Separately, a consent screen left in **"Testing"** publishing status issues
   refresh tokens that **expire after 7 days** — it must be published to
   "In production", whose only cost for a personal app is a one-time unverified-app
   warning screen.
7. **No email anywhere in the original prompt's phase list** — and the user's mail
   runs through Microsoft/Outlook, not Google. Added as Phase 4b, placed after
   Google Calendar so it can write into that phase's calendar, and before Phase 6
   so the Planner can see class times.

   Revised 2026-08-21 during the Phase 4b brainstorm: **Outlook *calendar* sync is
   dropped.** The user does not use Outlook Calendar and confirmed it holds
   nothing worth reading. That removes the entire multi-provider problem — the
   calendar schema stays Google-only, with no `provider` column, no merged week
   grid, and no second sync engine. What the user actually wanted was never two
   calendars in one view; it was that an email saying "class is cancelled
   Thursday" should reach their calendar. Phase 4b therefore delivers Outlook
   *mail* plus AI-assisted event extraction that writes through Phase 4's existing
   `createCalendarEvent`. Phase 6's dependency still holds by that route.

   Two facts verified against Microsoft's docs during that brainstorm: desktop
   apps are **public clients and must not use a client secret** (Client ID only,
   PKCE for the rest), and the Azure portal **rejects `http://127.0.0.1` redirect
   URIs** in its text box — so the registration uses `http://localhost`, whose
   port is ignored during matching, letting Phase 4's dynamic-port loopback server
   work unchanged.

One more cost flag not in the original prompt: **macOS notarization / Developer
ID code signing costs $99/year (Apple Developer Program)**. Not needed to build
and run SmartLife for yourself — Phase 9 packaging produces an unsigned `.app`
you open once via right-click → Open. Only relevant if you later want to hand
the packaged app to someone else without a Gatekeeper warning. Not planned
unless you ask for it.

  The final whole-branch review (run on the most capable model, after all 7 tasks had passed their own reviews) found a **Critical bug invisible to every per-task review and inherited byte-exact from the plan's own example code**: `useHome` computed today's date correctly as a *local* key, then passed it to `getEventsInRange`, which filters with SQLite's `date()` — and `date()` normalizes to **UTC**. Verified directly against this build: `date('2026-08-22T20:00:00-04:00')` returns `'2026-08-23'`. So an 8pm Eastern event was bucketed into tomorrow and never fetched. Every evening class, study group, and night shift was silently missing from the one section this phase exists to deliver, with the cutoff at `24:00 − |UTC offset|` local — 5pm in US Pacific, 8pm here. Worse, the plan also supplied the test that enshrined it (`expect(from).toBe(to)`), so a fully green suite said nothing about it. Fixed by requesting a padded ±1 day range and letting `buildToday`'s existing local-date filter make the exact selection, with the offsets built through the `Date(y, m, d + n)` constructor rather than millisecond arithmetic so DST cannot shift the boundary. Mutation-tested in both directions.

- [ ] **Phase 4 follow-up — a real bug in shipped code, found by the Phase 6a review.** `getEventsInRange` (`src/main/calendar/queries.ts`) filters with `date(start_at) <= ? and date(end_at) >= ?`, and SQLite's `date()` normalizes any offset or `Z` timestamp to **UTC**. Phase 6a worked around it locally with a padded range; the real fix belongs in the SQL and needs an `is_all_day` branch, because `date(start_at,'localtime')` would shift bare `YYYY-MM-DD` all-day rows back a day for western users. Not absorbed into Phase 6a on purpose — it is a Phase 4 correctness fix with its own test surface.
